# 提速手册：开发、修复到上架

目标是少来回、少补丁版本、少卡在人工门槛上。不降低 [发布门禁](release.md) 与 [测试证据](testing-troubleshooting.md) 的要求，只把它们前置、批量化、脚本化。来源见 [2026-09-27 复盘](../reports/retrospective-2026-09-27-speed.md)。

## 1. 需求：先列清单，再一次改完

- 「打磨/优化/全部修复」类请求：先按用户使用频率挑范围，逐项读代码列问题，标 P0（丢数据、写错、卡顿）/P1（高频不顺）/P2（细节）和「需实测」。用户确认后一次改完、一次发版，比逐条修逐条发快得多。
- 列问题时把**影响发版的产品决定**单独提出来问：隐私默认值、是否联网、是否改写用户笔记、数据存放位置（插件数据 vs 笔记属性）。这类决定在冻结候选之后才改，会让预扫描和草稿全部重来。
- 继承来的限制先查来源再遵守。另一个平台的审核约束（例如 Chrome 扩展为过审不抓网站图标）不自动适用于 Obsidian 插件；README 里的旧说法不是需求。拿不准时问一句，不要替用户保守。

## 2. 实现：已知宿主陷阱先避开

这些都在乔木插件里真实出过事故，写代码时直接避开，并留回归测试：

| 陷阱 | 后果 | 规避 |
| --- | --- | --- |
| `View` 子类上定义 `open` / `close` / `load` / `onload` 等同名方法 | 覆盖宿主生命周期，视图永远空白且无报错 | 私有工具方法换名（`openNote`）；源码级测试禁止这些方法名 |
| 从 promise 回调里返回 `Setting` 等带 `then` 的宿主对象 | 被当 thenable 递归解析，Obsidian 卡死 | 回调用花括号体，不隐式返回；测试扫描该模式 |
| 对所有已注册视图调用 `render()` | 后台恢复、尚未 `onOpen` 的视图字段为空而报错 | 渲染入口先判断已构建（如 `headEl` 存在） |
| 打开中的笔记用 `vault.process` 写 | 与编辑器缓冲冲突，可能冲掉用户正在输入的内容 | 文件在编辑器里打开时通过 `editor` 改；否则 `vault.process` |
| 输入框有焦点就跳过刷新 | 其他卡片一直不更新（例如快速记录后收件箱不变） | 照常重建，重建前记下卡片+输入框序号+值+光标，重建后还原；IME 组合中才延后 |
| 视图隐藏时也响应每个 vault 事件 | 后台反复重建、读全库 | `containerEl.isShown()` 为假只标记 stale，切回或 `layout-change` 时补刷 |
| 事件里全库扫描或逐个读文件（每次按键） | 大库卡顿 | 按名字推算候选文件（最近 N 天日记），按路径过滤事件，Top-K 代替全量排序 |
| 严格「快照必须完全一致」才写回 | 用户在别处改一字就失败 | 先按原行号核对，再按唯一原文重新定位；多处相同才拒绝 |

改写用户笔记的操作（勾选、删除、移动）默认给「撤销」，并按写入后的原文精确回滚。有成熟插件能力时优先调用其公开 API（例如 Tasks 的 `apiV1.executeToggleTaskDoneCommand` 处理完成日期与重复任务），缺失时降级并告诉用户差别。

## 3. 验证：宿主里脚本化，不靠用户点

用 `scripts/host_eval.py` 在 QA 库里跑真实操作，自动收集 console.error、未捕获异常与返回值：

```bash
python3 scripts/host_eval.py --vault <qa-vault> --reload <plugin-id> --file check.js --screenshot /tmp/after.png
```

- `check.js` 是 async 函数体：打开视图 → 找到元素 → `click()` / 设值后派发 `input`、`keydown` → 等待具体状态 → `return` 要核对的文件内容、属性、DOM 文本。退出码非 0 表示有异常或控制台错误。
- `plugin:reload` 之后旧叶子可能与 DOM 脱节（`containerEl.isConnected === false`）。每轮测试先 `detach` 旧视图再用插件自己的打开入口建新视图；「视图空白」先比较 `leaf.containerEl` 与 `view.containerEl` 是否都已连接。
- 文件在编辑器里打开时，磁盘读取会晚于编辑器保存；核对写入读 `editor.getValue()`，或先关闭该笔记的标签。
- 截图用于布局与主题检查（深色壁纸上的原生控件、对齐、溢出）；数据是否写对以文件内容为准。
- 怀疑回归时，用上一版本的构建（`git worktree` 检出、复用 `node_modules`）装进同一 QA 库对照，一次就能分清「环境问题」还是「本次引入」。
- QA 库可能同时被用户操作。发现页签、设置被改动时不要强行改回，换不打扰用户的核对方式并在报告里说明。

## 4. 上架：人工步骤一次集中

- 冻结候选前完成：`npm run check`、宿主脚本验收、README/隐私说明、版本号四处一致（manifest、package、package-lock 两处、versions.json）、`audit_release.py --scan-tips` 只剩旧项。
- 本地先清掉已知预扫描告警：CSS 的 `!important`、`:has`、`display: contents`、重复属性；TS 的冗余断言。扫描出的 Warning 与 Recommendation 记录去向，不要等扫描后再补一个提交。
- 官方预扫描、登录后台等需要账号的步骤，把候选 SHA、草稿 Release、资产摘要一次准备好，交给用户一步完成；自动化被权限拦截时不要换方式绕过，直接说明需要哪一步。
- 扫描之后又改代码（哪怕只是默认值），必须更新草稿 Release 的目标与资产并重扫；草稿未公开前可以替换资产，公开后只能发新补丁版本。
- 顺序不变：预扫描通过 → 公开同版本 Release → 匿名资产回读 → 合并让默认分支暴露新版本。

## 5. 连续补丁的信号

同一天出现第二个补丁版本，说明上一轮缺了宿主实测或冻结后又改。下一轮先补齐第 3 节的脚本，再改代码；移动端布局修复同时核对修复前后的安全区，避免「修一个间距引入另一个」。

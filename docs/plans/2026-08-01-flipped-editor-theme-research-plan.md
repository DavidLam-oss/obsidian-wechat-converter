## 1. 结论先行

这次应规划为两条互相独立的主题产品线，不能把 GitHub 仓库的主题揉进 Flipped Editor 的 Image Essay，也不能把外部主题的固定色板直接带进本项目：

1. **杂志叙事线**：以用户已经选定的 **Image Essay** 为唯一母版，做一套原创的图文叙事主题。它解决的是首图、正文图片、图注与章节之间的阅读节奏，不是简单换色。
2. **独立结构主题线**：逐套评估 obsidian-wx-open-source 的 7 个固定主题，但只判断其去掉固定色板后仍然成立的结构语言。通过筛选的候选应结合 AppleTheme 重新设计，作为主题选择器里的独立主题出现。

推荐第一批范围是：

- 先落地一个原创的“图文志”（暂定名，代码标识可用 image-essay）主题；它的结构独立，但所有强调色仍来自用户当前选择的主题色；
- 独立结构主题线先保留两个去色后仍有辨识度的方向：“章序”（编辑部式大号章节序列）与“框签”（硬边、标签和虚线层级）；这些是本项目暂定名，不沿用外部名称；
- “边页”（边框式观察笔记）和“疏文”（大留白长文）降为条件候选：去掉原仓库的橄榄橙或墨绿色板后，必须先证明仍与现有“纸张长文 / 优雅”有显著结构差异；
- 原仓库中依赖“绿 + 黄标记”或“红 + 白强对比”建立身份的两个主题不迁移；一旦改成任意动态主题色，它们剩余结构与本项目现有主题重复，新增价值不足；
- 原仓库的“极简主题”也不迁移，因为其最终实现复用了该仓库原有的语雀样式，并不是新增主题能力；
- 在没有获得单独授权或明确接受 AGPL 合规影响前，不复制该仓库或上游 gzh-design-skill 的主题代码、精确样式串、装饰 HTML、文案与素材。当前项目是 MIT，直接移植 AGPL 主题实现存在强 copyleft 许可风险。

本规划只负责调研、分流、范围和验证方案，不代表已授权修改主题代码、提交、推送或发布。

## 2. 需求判断与边界

需求类型：新功能 / 新流程方案（L2）。这是对主题目录、文章结构表达和真实公众号验证方式的扩展，需要在 OpenPrd 中先确认需求摘要，再进入正式 review / change / tasks。

主要服务对象是在 Obsidian 写作、希望减少二次排版的公众号创作者。第一版要让普通 Markdown 在图片不充分时仍然可读，在图片准备充分时明显获得杂志式图文节奏，同时保持现有复制和草稿同步的稳定性。

| 产品线 | 本次纳入规划 | 本次明确不做 |
| --- | --- | --- |
| Image Essay 杂志叙事线 | 原创主题、首图合同、普通图片与图注、章节节奏、无图降级 | 复刻对方品牌、编辑器 UI、示例文章、图片、CSS / JS；一次实现 Flipped 的另外 3 个模板 |
| GitHub 独立结构主题线 | 提取去色后仍成立的结构原则、重新命名、动态主题色适配、去重、许可证结论 | 把这些主题融入 Image Essay；保留外部名称或固定色板；无筛选地一次加入 7 套；直接复制 AGPL 实现 |
| 项目主题系统 | 复用 AppleTheme、用户可选主题色 / 自定义色、内联样式、动态主题列表、原生预览 / 复制 / 草稿同步 | 建第二套平行主题引擎；为新主题写死品牌色；把样式堆进 input.js 或仅对预览区生效 |
| 本轮交付 | 调研规划文档、推荐范围、风险与 evidence-plan | 实现、生成构建产物、commit、push、PR 或发布 |

## 3. 产品架构：两条主题线并列，不混合

~~~text
主题选择器
├── 现有主题
│   ├── 简约 / 经典 / 优雅
│   └── 纸张长文 / 网格文档 / Typo / 清爽媒体 / 彩色强调

│   └── 图文志（Image Essay 母版，原创实现）
~~~

这里的“独立”包括五层含义：独立的本项目名称、独立的主题配置、独立的动态色适配、独立的视觉验收样本、独立的许可证 / 来源记录。Image Essay 不引用这些结构主题的 token，也不提供外部主题名称组合。

## 4. Flipped Editor 调研：Image Essay 作为母版

### 4.1 四个模板的差异

四个模板不是单纯的颜色皮肤，而是文章结构模板：

| 模板 | 核心结构 | 对内容的要求 | 对本项目的处理 |
| --- | --- | --- | --- |
| Nature Magazine | 顶部大图，标题靠近或叠入首图 | 需要一张有封面构图能力的横图，标题区还要有安全留白 | 暂不做；后续可作为“封面叙事”独立变体 |
| **Image Essay** | 全宽首图，图片与文字连续推进 | 中等偏高；需要有叙事作用的图片、顺序和图注 | **当前唯一母版** |
| Poetic Minimal | 窄幅圆角首图、大留白、轻纸纹 | 中等；图片少也能成立，但文字必须短而有节奏 | 暂不做；后续可作为“诗性留白”独立变体 |
| Chapter Cards | 每个 H2 及其后续内容组成章节卡片 | 对 Markdown 章节结构要求高，需要稳定的 H2 层级 | 暂不做；需独立 DOM 重组能力 |

### 4.2 “像杂志一样排图文”对文章内容的真实要求

要求确实比普通公众号主题高，但不应要求用户先成为专业编辑。产品应把要求拆成“最低可用”和“最佳效果”：

| 内容条件 | 最低可用 | 最佳效果建议 |
| --- | --- | --- |
| 首图 | 可以没有；无图时降级为纸刊式标题开篇 | 1 张横向或接近 4:3、主体明确、可承担开篇的图片 |
| 正文图片 | 0 张也必须正常阅读 | 每 2–4 个自然段或每个主要章节 1 张，不为凑数重复插图 |
| 图片角色 | 普通图片沿用现有语义 | 显式区分首图、跨栏图、普通图；不要按尺寸或文件名猜用途 |
| 图注 | 没有图注时不生成空结构 | 说明地点、时间、对象或观点，而不是重复图片可见内容 |
| 文章结构 | 普通段落和标题可直接渲染 | H2 表示主要章节，图片放在它所解释的段落附近 |
| 图片质量 | 现有图片上传链路能处理即可 | 同一篇尽量统一色温、画幅倾向和视觉密度 |
| 文字节奏 | 长段也必须安全换行 | 段落更短，图片前后有承接句，避免连续大段说明淹没图片 |

因此，Image Essay 不能做成“只有图片够多才可用”的脆弱模板。推荐采用渐进增强：

- 无图：退化为稳定的纸刊长文，不出现空封面、大片留白或破碎图注；
- 有首图：启用杂志开篇；
- 有章节图片：形成图文节奏；
- 有显式图片角色：才启用跨栏等更强布局；
- 信息密度过高的表格、代码、公式和 Callout 仍使用兼容优先的现有组件，不强行“杂志化”。

### 4.3 Image Essay 的原创视觉合同

从参考站公开页面和计算样式确认到的共同基调可以作为方向，不作为要复制的代码：暖纸色、中文衬线正文、低饱和深褐文字、明显的章节呼吸感、克制细线和轻量图注。

这里的暖纸色和深褐色只描述母版的中性表面与正文可读性，不取代用户主题色。H2 细线、链接、强调、图注标记等可交互或强调角色必须继续从 AppleTheme 的动态主题色派生；用户选择蓝、绿、紫、橙等预设色或任意自定义色时，Image Essay 都要保持结构和对比度成立。

第一版建议重新设计并锁定以下记忆点：

- 公众号移动画布里有安静的纸刊气质，而不是网页卡片缩小版；
- 首图负责“开篇”，普通图片负责“推进”，图注负责“解释”，三者样式不同；
- H1 左对齐且克制，H2 用大间距切章，H3 用弱竖线定位；
- 引用使用细规则线或实体边框，不依赖伪元素；
- 不复制 Flipped 的产品名称、刊头、示例文本、图片、源 CSS、JavaScript 或品牌资产。

### 4.4 建议的图片角色合同

实现前需要在 OpenPrd review 中确认标记语法。规划层推荐“自动安全降级 + 显式增强”，而不是图片尺寸猜测：

| 角色 | 语义 | 无显式标记时的行为 |
| --- | --- | --- |
| hero | 文章首图 / 开篇图 | 可选择使用正文第一张图片，但必须是可关闭、可预测的规则 |
| wide | 强调性跨栏图 | 不自动猜；普通图片不会突然突破正文轨道 |
| regular | 正文叙事图片 | 所有普通 Markdown 图片默认使用 |
| caption | 图片说明 | 优先复用 alt / 现有图片说明能力；缺失时不显示空图注 |

第一阶段可先只实现 hero + regular + caption，把 wide 作为单独增强，降低复制到公众号后的宽度风险。

## 5. GitHub 独立主题线调研

### 5.1 已核实的仓库事实

调研固定到公开仓库提交 279525a374629e96f33bbbf8ae8409a19749050d（提交时间 2026-07-28 13:48:50 +08:00）：

- README 声明主题选择器固定暴露 7 套主题；测试也断言这 7 个名称；
- 主题在 src/themes.ts 以标签级 CSS 字符串描述，转换器还会为 6 个新增主题生成专属 H2 装饰 HTML；它不是一组可原样放入本项目的 CSS 文件；
- 输出依赖内联样式，这一点与本项目的公众号兼容方向一致；
- minimal 最终被重新赋值为原有 yuque 主题，所以“极简主题”不是值得单独吸收的新设计；
- README、LICENSE、NOTICE 和测试一致声明该仓库为 AGPL-3.0-or-later；NOTICE 说明 6 个新增主题来自上游 gzh-design-skill 的适配；
- 上游仓库的 LICENSE 同样声明 AGPL-3.0-or-later。GitHub API 显示 NOASSERTION 只是平台未识别自定义许可证文件，不表示没有许可。

### 5.2 本项目的动态主题色是硬约束

当前 AppleTheme 将“主题结构”和“主题色”分开：

- 用户可以选择蓝、绿、紫、橙、青、玫红、红、灰 8 个预设色，也可以选择任意自定义色；
- themeColor / customColor 会在设置变化后实时更新预览；
- 标题在开启“标题使用加深主题色”时使用对应深色，任意自定义色通过亮度计算获得深色；
- 链接、强调、引用边线等已经从动态主题色取值；部分主题仍有中性背景、正文色、边框色，这些属于可读性与表面角色，不应与用户主题色竞争。

所以候选主题必须通过“去色测试”：把外部主题的绿、红、橄榄、橙等品牌色全部拿掉，仅保留结构、间距、边框、圆角、字体层级和装饰几何，再换入本项目任一动态主题色。如果此时主题失去身份或可读性，就不应新增。

### 5.3 七套外部主题的结构价值与去色结论

| 外部主题（仅作来源指代） | 去掉固定色后剩余的结构 | 动态色适配判断 | 对本项目结论 | 本项目暂定名称 |
| --- | --- | --- | --- | --- |
| 极简主题 | 普通标题、常规引用和表格 | 几乎没有独立结构；本身还回退复用语雀主题 | **拒绝**：与现有“简约”重复 | 不命名 |
| 摸鱼绿 | 章节编号、圆角信息块、马克笔强调 | 主要身份来自绿黄配色；换成任意单主题色后与“清爽媒体 / 彩色强调”重叠 | **拒绝独立迁移**：个别通用组件原则可回到现有主题优化，但不新增主题 | 不命名 |
| 红白色系 | 章节徽标、粗边框、强提示块 | 主要身份来自红白强对比；动态色后只剩常规高强调模板 | **拒绝独立迁移**：若未来需要活动 / 警示场景，应从本项目需求重新设计 | 不命名 |
| 石墨极简风 | 大号淡章节数字、编辑部式上下层级、细规则线 | 去掉黑灰色板后，章节序列与留白仍成立；主题色只承担编号 / 规则线强调 | **调整后采用**：结合 AppleTheme 重做，优先评审 | **章序**（暂定） |
| 留白禅意风 | 大留白、衬线层级、短分隔线、低密度表格 | 可用动态色，但与现有“优雅 / 纸张长文”结构重叠明显 | **条件采用**：只有去重评审证明新增价值才保留 | **疏文**（暂定） |
| 摸鱼票据风 | 票据边框、硬阴影、虚线、标签块 | 去掉绿色后结构仍很强；主题色可用于标签、章节号和重点线 | **调整后采用**：需要控制硬阴影和微信兼容，优先评审 | **框签**（暂定） |
| 橄榄手记 | 手记边框、分区框、轻量标签和观察笔记结构 | 去掉橄榄橙后辨识度下降，但边框式内容组织仍可能成立 | **条件采用**：先与“纸张长文”去重，再决定是否值得独立主题 | **边页**（暂定） |

暂定名称只用于规划辨认，不是最终产品命名。命名验收标准是：不包含外部项目原名或其标志性颜色词；说明结构和阅读感受；与本项目现有主题名称语气一致；最终在视觉方向确认时一并锁定。

### 5.4 许可证结论

当前项目的 LICENSE 和 package.json 均为 MIT，而参考仓库及主题上游是 AGPL-3.0-or-later。规划建议把可选路径分清：

| 路径 | 可以做什么 | 代价 / 风险 | 推荐度 |
| --- | --- | --- | --- |
| 直接移植 AGPL 主题实现 | 复制样式串、装饰 HTML 或做近似改写 | 可能使组合后的插件需要遵守 AGPL；还涉及 NOTICE、源码提供和分发义务；需正式法律 / 许可判断 | 不推荐作为默认路径 |
| 向权利人取得单独授权 | 在约定许可下使用指定主题 | 需要书面明确范围、版本、署名、商业分发和衍生修改权 | 可选，若希望高度还原应优先谈授权 |
| Clean-room 原创重设计 | 只参考高层审美方向与功能需求，由本项目重新定义 token、组件和 HTML | 仍需保留调研隔离、避免精确复制有独创性的表达 | **推荐** |
| 仅列为外部灵感 | 不进入代码，只保留参考链接与差异说明 | 视觉收益不落地 | 风险最低 |

这不是法律意见。进入实现前至少要由维护者明确选择“单独授权 / 接受 AGPL 影响 / clean-room 原创”之一；在此之前，计划默认采用 clean-room 原创重设计。

## 6. 与当前项目的融合方式

当前分支已经有 8 套主题，而不只是早期文档中的 3 套：简约、经典、优雅、纸张长文、网格文档、Typo、清爽媒体、彩色强调。新增主题前必须先做目录去重，避免主题选择器变成同质皮肤堆积。

外部参考不能作为一块完整 theme object 搬入。融合单位应拆成三层：

| 层级 | 从外部参考中可以研究什么 | 必须使用本项目什么能力 |
| --- | --- | --- |
| 结构层 | 章节编号、票签边框、虚线、分区框、图片角色、标题与正文节奏 | AppleTheme 配置、标题构造器、原生序列化和现有标签语义 |
| 颜色层 | 只研究对比关系，例如“强调 / 次要 / 表面 / 边框” | 用户当前 themeColor / customColor、标题染色开关和本项目中性色 |
| 产品层 | 适用内容、主题之间的差异和选择理由 | 本项目自己的名称、说明文案、设置迁移、回退行为和验收样本 |

如果某个结构必须绑定原来的绿色、红色或橄榄色才能被认出来，它就不符合本项目主题模型，应被拒绝，而不是给动态色系统开例外。

### 6.1 共用接入架构

两条产品线都复用现有 AppleTheme，不新建平行引擎：

~~~text
用户选择结构主题 ───────────────┐
        │                       │
        ▼                       ▼
AppleTheme 结构配置      用户主题色 / 自定义色
        │                       │
        ├── 标题装饰            ├── 强调色
        ├── 间距与密度          ├── 加深标题色（可选）
        ├── 边框与表面角色      └── 透明浅色派生
        │                       │
        └──────────┬────────────┘
                   ▼
       标签级内联样式与必要结构节点
                   ▼
       原生预览 / 复制 / 草稿同步
                   ▼
           自定义 CSS 后置覆盖
~~~

Image Essay 额外需要一个小而明确的“图片角色 / 文章结构”层，但它不应侵入 GitHub 独立结构主题。独立结构主题应尽量只依赖 AppleTheme 的样式合同；若某套必须用章节编号 H2，则将编号能力设计成可复用的标题装饰构造器，而不是复制参考仓库的 HTML。

### 6.2 动态颜色角色合同

| 颜色角色 | 来源 | 可用于 | 不可用于 |
| --- | --- | --- | --- |
| accent | getThemeColorValue() | 链接、章节号、票签、重点边线、强调文字 | 大面积正文背景或低对比正文 |
| accent-readable | 根据 accent 与当前表面的对比度选择原色或安全加深色 | 链接和必须承载文字的强调角色 | 假定任意自定义色在白底上都可直接阅读 |
| accent-deep | 以现有 getHeadingColorValue() 为入口，并补足必要的对比度保护；遵守“标题使用加深主题色”开关 | 需要染色的标题和高权重标记 | 绕过用户开关强制染标题 |
| accent-soft | 从 accent 计算的透明浅色 | 引用 / Callout / 标签的浅表面 | 写死绿色、红色或橄榄色浅底 |
| text / muted | 主题中性可读色 | 正文、图注、辅助信息 | 跟随任意亮色导致正文对比不足 |
| surface / border | 主题中性表面与边框 | 纸面、卡片底、分隔线、表格边框 | 成为第二套固定品牌色 |

新结构主题不得引入与 accent 并列的固定第二强调色。若确实需要双色层级，只能使用 accent 的深浅 / 透明派生与中性色；不能保留原参考主题的“绿 + 黄”“红 + 白”“橄榄 + 橙”组合。

现有任意自定义色只是输入能力，并不自动保证文字对比度。亮黄、浅粉等颜色可安全用于线条、底纹和几何标记，但不一定能直接作为白底文字色；实现方案应为需要承载文字的角色增加对比度判断或安全回退，而不是把当前简单加深逻辑当成已解决的可访问性保证。这个能力应作为 AppleTheme 共用颜色工具完善，不能只为某一套新结构主题写特例。

## 7. 分阶段实施建议

### 阶段 0：OpenPrd 需求确认与证据样本

确认两条主题线的边界、第一批结构主题数量与本项目命名、Image Essay 图片角色语法和许可证策略。冻结两类 Markdown 验收样本：

- Image Essay 样本：无图、单首图、多图、带图注、长文、表格、代码、Callout、Mermaid、数学；
- 结构主题样本：同一份通用文章跨所有候选主题横向比较，并至少在蓝、红、绿、紫、橙、灰与两个自定义极端色上做动态色矩阵。

### 阶段 1：Image Essay 单独落地

只实现 Image Essay 母版，不捎带 GitHub 结构主题。先完成 hero + regular + caption、无图降级、主题字号比例、动态主题色和公众号内联兼容。

### 阶段 2：结构主题去色与去重评审

以现有 8 套主题作为对照，只评审去掉来源固定色后仍成立的本项目结构方向，不做混合稿：

1. 章序：大号章节序列与编辑部式层级；
2. 框签：硬边、虚线与标签结构；
3. 边页：边框式观察笔记（条件候选）；
4. 疏文：大留白与衬线长文（条件候选）。

每个方向都要同时展示至少 3 个差异明显的用户主题色，证明结构不是靠某个固定色成立。用户逐套确认方向与名称后再决定哪些进入实现；未确认的候选不写入项目主题配置。

### 阶段 3：结构主题逐套实现

每套作为独立 task 落地和验证，不用一个大改一次塞入多套。建议先做章序与框签；边页和疏文只有在去重评审通过后才排期。原仓库依赖固定绿黄 / 红白配色的方向不再作为独立主题追加。

### 阶段 4：真实公众号验证与目录收口

每套主题都必须在插件预览、复制到公众号编辑器、同步草稿三个输出面验证。根据对比结果决定保留、调整或撤下，不以本地 HTML 预览代替真实公众号证据。

## 9. 第一版验收标准

Image Essay 第一版应满足：

1. 在主题选择器中作为独立主题出现，不使用 Flipped Editor 的品牌名；
2. 无图文章不破版，有首图时形成明确开篇，多图时形成稳定图文节奏；
3. 图片角色行为可预测，不按尺寸、文件名或主观算法偷偷猜测；
4. 根容器、标题、正文、引用、列表、表格、图片、图注、链接、代码都有自洽内联样式；
5. 预览、复制与草稿同步使用同一基础 HTML，复杂内容不被主题结构破坏；
6. 不包含 Flipped 的源代码、品牌、图片、示例文案或远程字体；
7. 在所有预设色与自定义色下保持主题结构、文字对比和强调层级成立；不强制暖棕色成为第二强调色。

每套 GitHub 线结构主题应满足：

1. 单独列在主题目录，不是 Image Essay 变体；
2. 使用本项目重新确认的名称；代码标识和用户文案均不沿用外部主题名称；
3. 与现有 8 套主题有可见且可解释的结构差异，不只是换一个主色；
4. 全部强调色从用户当前主题色派生，不写死来源主题的绿色、红色、橄榄色、橙色或黄色；
5. 使用本项目原创的 token、标题构造和样式表达，或有明确的单独授权 / AGPL 决策记录；
6. 不复用外部仓库的精确 CSS 串、专属装饰 HTML、英文标签映射、示例内容或素材；
7. 每套独立通过动态色矩阵、自动化和真实公众号验证，失败时可单独撤下，不影响 Image Essay 和现有主题。

## 10. 待用户确认的最高价值决策

当前已经确认：

- Image Essay 是 Flipped 线母版；
- GitHub 仓库主题必须单独列出，不能融入 Image Essay。
- 新主题必须服从本项目的动态主题色与自定义色，不保留外部固定色板；
- 只吸收可迁移结构，并结合 AppleTheme、现有渲染链和公众号兼容要求重新设计；
- 所有新主题使用本项目自有名称，不沿用外部主题名。

下一步只需要确认第一批结构方向与暂定命名：是否先评审 **章序** 与 **框签**，把 **边页** 和 **疏文** 保留为去重通过后才进入的条件候选？这些名称仍可在正式视觉评审时继续调整。

确认后再按 OpenPrd canonical capture 路径写入用户已确认事实，生成正式 requirement / review / change / tasks；这一步仍不等于开始实现。
